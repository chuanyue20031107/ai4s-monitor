# AI4S Monitor 一次性全量分析提示词

请你直接完成 AI4S Monitor 的全量未分析情报分析，并在全部完成后一次性保存到 GitHub。你负责分析；GitHub Actions 只负责校验、导出和 Pages 发布。

## 强制执行规则

启动时读取 main 分支的 AGENTS.md、docs/chatgpt-analysis.md、data/queue.json、client/public/data/articles.json、data/receipts.json、data/raw/ 和现有 data/inbox/。动态计算当前所有未完成记录；禁止使用 723、385 或任何预设数量。

建立唯一本地运行目录 work/full-analysis-<UTC 时间>/，写入 manifest.json、checkpoint.json、results/、errors.json。manifest 固定本次启动目标 ID、启动时 queue.updatedAt、每个 raw.contentHash 和 targetCount。每次恢复或提交前重新读取 queue、raw 和 accepted receipts；执行期间新出现的 pending 记录加入目标，直到连续一次完整扫描得到 pending=0。

执行内部循环，循环条件是仍有未完成目标：

1. 取下一组尚未分析目标，在本地读取每个最新 data/raw/<id>.json。
2. contentStatus 不是 ready 或正文不足时，按原 URL 使用仓库现有采集/补抓能力获取正文；遵守 robots、登录、验证码和付费墙边界。成功后重新读取 raw 和 contentHash。
3. 逐条生成真正的中文 AI4S 分析。done 必须包含 category、summary（40–2500字）、score（1–5）、importanceReason、contentType、moatTags、1–5个逐字 evidence、limitations、analyzedAt；evidence 必须完整出现在当前 raw.content。确认是导航、版权、招聘、采购或其他无关页面才标记 discarded 并写明原因；证据不足标记 failed 或保留 pending，不能伪造 done。
4. 立即把结果写入本地 results/，并更新 checkpoint；不要提交 GitHub，不要修改远端 queue、receipts 或前端文件。
5. 继续下一组，直到 manifest 中每条目标都有当前 contentHash 对应的合法结果。不要因为批次数量、上下文压缩、工具输出上限或 Actions 等待而结束；恢复时从 checkpoint 继续。
6. 全部结果生成后，在本地统一校验：每个目标恰好一个结果；ID、contentHash、字段、分类、评分、证据摘录和状态全部合法；done 的正文充分；没有重复、遗漏、过期哈希或模板摘要。校验失败就回到内部循环修复。
7. 只有统一校验完全通过后，才一次性生成全部 data/inbox/<UTC>-full-*.json。允许因单文件大小拆成多个文件，但所有文件必须在同一个 Git commit 中提交，禁止中间 commit。
8. 提交后等待 publisher，读取 data/receipts.json；任何 rejected 批次都在本地修复后重新执行统一校验并使用一个新的最终 commit。确认 Actions 的 deploy 作业成功，再读取 Pages 实际 articles.json、analysis-status.json 和 AI已分析列表。
9. 最终重新扫描实时 queue 和 raw。只有目标全部是当前有效 done、缺正文为0、failed/pending为0、实时 pending=0 且 Pages 验证成功，才报告“全部未分析情报已分析并展示”。报告 targetCount、最终处理数、done/discarded/failed、缺正文数、新增数、剩余 ID、最终 commit、Actions URL 和 Pages URL。

## 绝对禁止

禁止把 GitHub 入队、拆批、workflow success 或提交成功当成分析完成；禁止固定数量、只处理前 N 条、凭标题补写、复制模板、伪造 contentHash、把 discarded/failed 算作 done、force-push、添加模型 API 密钥或外部数据库。
